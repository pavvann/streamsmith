## What makes this server refuse

The server is **fail-closed**: it only answers from a deployment it has just verified against the receipt. On startup and
every 60 s it

1. re-reads the receipt (`RECEIPT_PATH`) and checks its `packageHash`, `outputModuleHash`, `parametersHash`,
   `protoDescriptorHash` and `sinkSchemaHash` still equal the ones this server was generated for -> otherwise `receipt_mismatch`;
2. reads `system.columns` for 4 expected tables (`vault_flows`, `share_value_observations`, `vaults`, `share_transfers`) and compares a normalized
   column-set hash with `manifest.json` -> otherwise `schema_mismatch` (with `expected` and `actual` column sets and a diff);
3. asks `BASE_RPC_URL` for `eth_chainId` / `eth_blockNumber` and ClickHouse for the sink head (`max(_block_number_)`);
   wrong chain -> `chain_mismatch`; `chainHead - headBlock > MAX_LAG_BLOCKS` (default 300) -> `stale_data`;
4. if any of the above could not be evaluated (ClickHouse or RPC unreachable, receipt unreadable, or the last successful
   check is older than 3 intervals) -> `check_unavailable`.

A refusal is returned by every data tool as
`{ "refused": true, "reason": "<reason>", "detail": "...", "expected": ..., "actual": ..., "checkedAt": "...", "provenance": {...} }`
with `isError: true`. `pipeline_status` never refuses; it reports the verdict.

Every successful response carries `provenance`: `packageHash`, `outputModuleHash`, `parametersHash`, `protoDescriptorHash`,
`sinkSchemaHash`, `schemaColumnSetHash`, `deploymentMode`, `deploymentId`, `chainId`, `headBlock`, `headTimestamp`, `chainHead`,
`lagBlocks`, `observedWindow` and `checkedAt`. `observedWindow` is measured on the data, never on configuration: `observedFromTimestamp` /
`observedToTimestamp` are min/max of the window column over live rows, `startTimestamp` / `endTimestamp` are this query's bounds
(`hours` back from the newest row, or the whole observed window when `hours` is null).

SQL is read-only and parameterized: identifiers come from the manifest, values are bound as ClickHouse query parameters
(`{name:Type}` + `param_name`), `readonly=1`, `max_execution_time` and a 10 s client timeout on every request, `LIMIT` <= 500.
Wide numerics (UInt256, Decimal) are returned as strings; 64-bit integers are quoted by ClickHouse's JSON output as well.

## Tools

### `vault_flows` (table: `vault_flows`)

ERC-4626 Deposit/Withdraw logs on the configured vaults (table vault_flows), newest first, within a trailing window of the observed data. caller, owner and receiver are kept separate; assets/shares are raw base-unit strings plus normalized decimals; execution_rate is assets per whole share implied by this single flow (deposit-implied or withdraw-implied per direction). Rows with meta_valid = false carry "0" placeholders.

| argument | type | meaning |
|---|---|---|
| `vault` | enum of 2 receipt vault(s), optional | Restrict to one vault. Only the 2 vault(s) pinned by the Deployment Receipt are accepted (lowercase 0x hex). |
| `direction` | enum `deposit` or `withdraw`, optional | Restrict to deposits or withdrawals. |
| `windowHours` | integer 1..2160, default 24 | Trailing window in hours, measured back from the newest observed row (not from now). 1..2160, default 24. |
| `limit` | integer 1..500, default 100 | Maximum rows returned, 1..500 (default 100). |

Columns: `id` (String), `chain_id` (UInt32), `block_number` (UInt64), `block_hash` (String), `block_timestamp` (UInt64), `tx_hash` (String), `log_index` (UInt32), `vault` (String), `caller` (String), `owner` (String), `receiver` (String), `direction` (String), `assets_raw` (UInt256), `shares_raw` (UInt256), `assets_normalized` (Decimal(38, 18)), `shares_normalized` (Decimal(38, 18)), `asset_decimals` (UInt32), `share_decimals` (UInt32), `execution_rate` (Decimal(38, 18)), `meta_valid` (Bool), `call_ok` (Bool), `call_error` (String).

### `share_value_observations` (table: `share_value_observations`)

Point-in-time share-value observations (table share_value_observations): convertToAssets(10^share_decimals), totalAssets and totalSupply read at sampled blocks (block_number % sample_interval_blocks == 0). Rows with call_ok = false are emitted with "0" placeholders and call_error; nothing is interpolated between samples.

| argument | type | meaning |
|---|---|---|
| `vault` | enum of 2 receipt vault(s), optional | Restrict to one vault. Only the 2 vault(s) pinned by the Deployment Receipt are accepted (lowercase 0x hex). |
| `windowHours` | integer 1..2160, default 24 | Trailing window in hours, measured back from the newest observed row (not from now). 1..2160, default 24. |
| `limit` | integer 1..500, default 100 | Maximum rows returned, 1..500 (default 100). |

Columns: `id` (String), `chain_id` (UInt32), `block_number` (UInt64), `block_hash` (String), `block_timestamp` (UInt64), `vault` (String), `sample_interval_blocks` (UInt32), `assets_per_share_raw` (UInt256), `assets_per_share_normalized` (Decimal(38, 18)), `total_assets_raw` (UInt256), `total_supply_raw` (UInt256), `call_ok` (Bool), `call_error` (String).

| `windowHours` | integer 1..2160, default 24 | Trailing window in hours, measured back from the newest observed row (not from now). 1..2160, default 24. |
| `limit` | integer 1..500, default 100 | Maximum rows returned, 1..500 (default 100). |

### `share_value_growth` (view: `share_value_growth`)

Per configured vault: first and last share-value observation in the observed window (block numbers, timestamps, assets per share) and growth = last / first - 1. Only observations with call_ok = true; never interpolated.

| argument | type | meaning |
|---|---|---|
| `vault` | enum of 2 receipt vault(s), optional | Restrict to one vault. Only the 2 vault(s) pinned by the Deployment Receipt are accepted (lowercase 0x hex). |
| `windowHours` | integer 1..2160, optional (omit = whole observed window) | Trailing window in hours, measured back from the newest observed row. Omit for the entire observed window. 1..2160. |
| `limit` | integer 1..500, default 100 | Maximum rows returned, 1..500 (default 100). |

Columns: `vault` (String), `first_block_number` (UInt64), `first_block_timestamp` (UInt64), `first_assets_per_share_normalized` (Decimal(38, 18)), `last_block_number` (UInt64), `last_block_timestamp` (UInt64), `last_assets_per_share_normalized` (Decimal(38, 18)), `growth` (Nullable(Float64)), `observed_hours` (Float64), `observation_count` (UInt64).

### `pipeline_status` (status)

Health of the pipeline behind the other tools: receipt identity (package hash, module hash, parameters hash), live ClickHouse schema check against the receipt, sink head vs chain head (lag in blocks), the fail-closed verdict and its reason, and the policy in force. Call this before acting on data; every other tool refuses when this reports refused = true.

_no arguments_

## Run

```bash
pnpm install                      # from the workspace root
export CLICKHOUSE_URL=http://localhost:8123 CLICKHOUSE_USER=ro CLICKHOUSE_PASSWORD=ropass CLICKHOUSE_DATABASE=vaultflows
export BASE_RPC_URL=https://mainnet.base.org
node bin/server.js                # stdio MCP server (Node >= 22.18)
```

## Files

- `manifest.json` — tools, argument schemas, expected column sets, hashes (its sha256 goes into the receipt as `mcpManifestHash`).
- `receipt.json` — copy of the Deployment Receipt the server was generated from; re-read every cycle.
- `src/tools.generated.ts` — zod input shapes and tool specs; `src/server.ts` — entry point; `src/runtime/` — fail-closed guardian, SQL builder, ClickHouse and RPC clients.
