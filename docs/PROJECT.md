# Project Draft v2: Streamsmith

*ETHOnline 2026 · v2 · Sept 9, 2026 · revised after the Claude × Codex design discussion (`docs/research/codex-discussion.md`) · v1 kept at `docs/PROJECT-v1.md`*

**Tagline:** One prompt. A verified Substreams pipeline, live and agent-ready.

**Precise description:** Streamsmith is a reproducible promotion and provenance layer for AI-generated Substreams.

---

## 1. Thesis (this paragraph goes at the top of the README)

Building a blockchain data feed usually means writing indexer code, testing it, operating a database, and then teaching every application how to trust the result. Streamsmith turns one plain-language request into a tested Substreams pipeline, deploys it against live chain data, and creates a receipt connecting the exact code, configuration, database schema and MCP tools; those tools refuse to answer when the data is stale or mismatched. We demonstrate it by tracking tokenized savings vaults and letting a policy-controlled Privy business wallet move real USDC using the resulting live data. One prompt becomes a verifiable data service an agent can safely use.

## 4. What we build

### 4.1 Streamsmith (plugin, the reusable artifact)

Composes the official Substreams skills into a promotion pipeline. The skills generate the code; Streamsmith owns everything after the code exists.

1. **Gate** (`gate.yaml` → script with exit codes): `substreams build`, fixed-range `substreams run`, assertions (rows produced, known vault present, RPC success threshold, deterministic rerun over the same range, **normalized protobuf-descriptor hash equals the expected public contract**). If the schema drifted, the gate fails.
2. **Publish**: pack and publish the `.spkg`; capture package hash and registry timestamp.
3. **Deploy**: hosted sink on The Graph Market via the Portal API, or a self-managed `substreams-sink-sql` on a VPS if the hosted beta fights us; `deploymentMode` recorded honestly. Poll head and lag.
4. **Receipt**: the central artifact.

```json
{
  "packageHash": "...", "outputModule": "...", "protoDescriptorHash": "...",
  "parametersHash": "...", "sinkSchemaHash": "...", "mcpManifestHash": "...",
  "deploymentMode": "graph-market-hosted | self-managed-sink",
  "deploymentId": "...", "chainId": 8453, "startBlock": 0, "headBlock": 0, "lag": 0,
  "gate": { "range": "A:B", "assertions": ["rows>0", "known-vault-present", "descriptor-hash-match"], "passed": true },
  "registryPublishedAt": "...", "deployedAt": "..."
}
```

5. **Expose**: generate a TypeScript MCP server from the protobuf descriptors and the receipt: typed semantic tools, read-only parameterized SQL, row limits and timeouts, provenance (package hash, parameters hash, head, lag) in every response, and **fail-closed** behavior when the live deployment's package, schema, or lag no longer matches the receipt.
6. **Record**: run manifest (starting commit, prompt hash, tool versions, ending commit, receipt hash) and a case study in the skills-repo format.

### 4.2 erc4626-flows (package, the contribution)

Imports Pinax `erc4626` (raw Deposit/Withdraw, matched by signature across every vault on the chain). Emits:

- `VaultFlow`: chain, block, tx, log index, vault, **caller, owner, receiver** (kept separate), raw `assets` and `shares`, normalized values only when metadata is validated, `deposit_execution_rate` or `withdraw_execution_rate`, call-status flags.
- `ShareValueObservation` (parameterized module: vault list, interval `K` blocks, sampled on `block.number % K == 0`): `assets_per_share` via `convertToAssets(10^shareDecimals)`, `total_assets`, `total_supply` as point-in-time observations, per-call success/error status, block number and hash, timestamp, chain id. **Never interpolated between samples.**
- `ShareTransfer` (Should, if time): ERC-20 transfers of vault shares excluding the mint/burn paired with Deposit/Withdraw. Called **share migration**, never "collateral reuse".
- Vault validation: first sight probes `asset()`, `decimals()`, `totalAssets()`, `convertToAssets()`; failures mark the address non-compliant and drop it. Labeled heuristic in the README.

ClickHouse (from-proto, insert-only) tables `vault_flows`, `share_value_observations`, `vaults`, plus views `vault_flows_24h` and `share_value_growth` (over the observed window). Deterministic row ids for restart safety. Parameters (vault list, interval) are hashed into the receipt.

Metric naming rules: "execution rate", "share value", "observed-window share-value growth over N hours, blocks X–Y". Banned words: yield, APY, share price, TVL, risk score.

### 4.3 Vaultpilot (app, the execution proof)

- Business wallet on Privy, owned and configured by humans. Agent is an **additional signer** under a policy: `earn_deposit` and `earn_withdraw` allowed only for the two pinned Privy vault ids (Gauntlet USDC Prime, Steakhouse Prime Instant, Base mainnet; ids are per-app and issued after deploying a fee wrapper in the dashboard), per-action cap via `action_request_body.amount`. Privy aggregations do not cover Earn, so the rolling daily cap is enforced app-side and disclosed as such. Anything else is denied by default. A human can pause or replace the signer.
- **Rule:** rotate to the other approved vault when observed-window share-value growth differs by more than a configured minimum (covering gas and friction), subject to a cooldown, an outflow guardrail on the destination, a staleness refusal from `pipeline_status`, a `maxWithdraw` and liquidity check, exclusion of our own withdrawals from the guardrail, and an idempotency key. Two sequential transactions: if withdraw succeeds and deposit fails, USDC stays idle and the treasurer is alerted.
- Demo: (1) agent attempts an unapproved vault, Privy denies; (2) agent proposes an approved, below-cap action from the live signal, Privy executes; real Base tx hashes. Above-policy actions are "denied and returned to the treasurer". No intents, no quorum unless they work on the first try.
- UI: one screen. Position, the two observations with exact window, decision and rule, policy result, pipeline provenance, tx links, who controls the wallet and how to revoke the agent.
- Funding: about 50 USDC on Base. Initially fund whichever approved vault has the lower observed growth so a real rotation is possible; never lower the threshold to manufacture one.

## 5. The forensic one-prompt protocol

- Clean tagged commit contains: `specs/vaultflows.proto` (public contract), `streamsmith.yaml` (vaults, interval), `gate.yaml`, tests and fixtures, Streamsmith. **No** Rust, manifest, sink schema, MCP, package, or receipt.
- At recording start, on screen: `git status --porcelain`, `git rev-parse HEAD`, `git tag --points-at HEAD`, `date -u`.
- Screen capture plus a timestamp-preserving terminal recording (asciinema).
- **One human instruction, verbatim:**

> Using the installed official Substreams skills and Streamsmith, build a reusable Base pipeline for ERC-4626 vault activity. Implement the public interface in `specs/vaultflows.proto`, using the vault addresses and sampling interval in `streamsmith.yaml`; include normalized deposit and withdrawal facts and fixed-interval `convertToAssets` observations. Do not modify the schema, tests, or gate requirements. Work autonomously until `gate.yaml` passes, then publish the package, deploy it to the configured ClickHouse sink, generate its typed MCP tools, and write a complete Deployment Receipt. If a requirement cannot be satisfied, stop with evidence rather than weakening or bypassing it.

- No human follow-up inside the run. The agent may iterate on compiler and gate failures itself. We do not stage failures.
- The package that passes the gate and post-run human review becomes the published v0.1.0. If the output is unsafe or unmaintainable, discard the run, improve the public tests, reset to the tag, run again. Never repair a recorded run by hand and call it autonomous. The final recording is the accepted run.
- Publish: full transcript, diff from the tag, run manifest, uncut recording's SHA-256, registry and deployment timestamps.
- The hand-built reference implementation is used only to design the schema, tests and assertions; disclosed in `AI-USAGE.md`.
