**EVM gotchas that will bite in the first hour.** (a) Native/ERC-20 USDC decimal mismatch (18 vs 6) — never mix raw values; the ERC-20 `balanceOf` truncates. (b) `transferWithAuthorization` that fully drains a never-used account (0 nonce, no code) reverts on testnet — a fix is planned. (c) Blob txs rejected; beacon-roots contract absent; consecutive blocks may share a timestamp — order by block number. (d) A blocklisted address makes value transfers revert at runtime (gas still consumed). (e) EIP-7708 native `Transfer` logs exist (18-dec) in addition to the ERC-20 `Transfer` (6-dec) — indexers must not double-count.

### 1.2 Circle Agent Stack (CLI, Agent Wallets, Nanopayments, Marketplace, Paymaster, Gateway, CCTP)

**Circle CLI** — `npm i -g @circle-fin/cli` (v1.0.0 released 2026-08-13; Node ≥ 20.18.2). Command groups: `wallet (login|logout|status|create|list|limit|balance|fund|transfer|swap|sign message|sign typed-data|execute|import)`, `services (search|inspect|pay)`, `bridge (transfer|status|get-fee)`, `gateway (balance|deposit|withdraw)`, `blockchain`, `transaction`, `contract (address|query)`, `skill (list|info|install|update)`, `terms accept`, `telemetry`. Every command supports `--output json`. `CIRCLE_ACCEPT_TERMS=1` for non-interactive first run.

**Agent Wallets.** Created automatically on all supported chains at `circle wallet login you@example.com [--testnet]` — **email OTP** login (non-interactive flow: `--init` returns a request ID, then `--request <id> --otp <code>`; the agent can only log in if it can read the inbox). 2-of-2 MPC user-controlled wallets; key shares never exposed to the agent; gas **sponsored** (capped, fair-use); sanctions screening on every transfer; max 5 agent wallets/user; sessions 28 days, stored in OS keychain. Chains: ARB, AVAX, BASE, ETH, MONAD, OP, MATIC, UNI (mainnet+testnet) and **Arc = `ARC-TESTNET` only** (no Arc mainnet yet). Testnet funding: `circle wallet fund --address 0x… --chain ARC-TESTNET` draws **20 USDC from the faucet**. `circle wallet execute "approve(address,uint256)" … --contract … --chain …` executes arbitrary contract writes; `circle wallet sign typed-data` signs EIP-712.
**Spending policies (`circle wallet limit set --per-tx --daily --weekly --monthly`, `--rule-type recipient-allowlist|recipient-blocklist|contract-allowlist|contract-blocklist`) are MAINNET ONLY** and confirm by a second email OTP. So "Circle policies on Arc" is not demoable in one wallet.
Fees: gas $0; CCTP fast-transfer fee + $0.05 forwarding on bridges; swaps 2 bps; Gateway protocol fee 0.5 bps cross-chain (free same-chain).

**Nanopayments / Gateway.** Gas-free sub-cent USDC payments: buyer deposits once into `GatewayWallet` (one onchain tx), then signs **EIP-3009 `TransferWithAuthorization` typed data against the `GatewayWalletBatched` domain** per request (zero gas); seller (or facilitator) submits to Gateway; Gateway verifies in an AWS Nitro Enclave and settles net positions in batches onchain. **EOA signatures only — no ERC-1271** (Circle SCAs and other smart wallets can't be nanopayment buyers; Privy server wallets and Ledger EOAs can). Chains with Nanopayments: all Gateway EVM chains incl. **`arcTestnet`**; deposit finality **~0.5 s on Arc testnet** vs **13–19 min on Base/Arb/Op/Eth Sepolia** (use Arc for demos!). SDK: `npm i @circle-fin/x402-batching @x402/core @x402/evm` — seller: `createGatewayMiddleware({ sellerAddress, facilitatorUrl: "https://gateway-api-testnet.circle.com" })` then `app.get("/x", gateway.require("$0.01"), …)`; buyer: `new GatewayClient({ chain: "arcTestnet", privateKey })` → `deposit("1")`, `supports(url)`, `withdraw`, `searchTransfers`; or `CompositeEvmScheme(new BatchEvmScheme(signer), new ExactEvmScheme(signer))` registered on an `@x402/core` client for automatic Gateway-vs-onchain fallback. CLI path: `circle gateway deposit --amount 5 --address … --chain ARC-TESTNET --method direct`, `circle services search "weather"`, `circle services inspect <url>`, `circle services pay <url> --address … --chain … --max-amount 0.01 [--estimate] [-X POST -d …]`.

**Agent Marketplace** (launched 2026-07-31): 600+ x402 services, sanctions-screened payout wallets, health-checked; keyless Discovery API `GET https://api.circle.com/v2/x402/discovery/resources` (14 filters; CAIP-2 networks; x402 Bazaar schema; OpenAPI/A2A discovery). "Get listed" = submit a form after your service returns valid 402s. Third-party seller tools: Blockrun, Proceeds (supports Arc), Sponge, x402scan.

**Starter kits** (`github.com/circlefin/agent-stack-starter-kits`, Bun workspace): six kits — LangChain Deep Agents, Claude Agent SDK, Mastra, OpenAI Agents, Vercel AI SDK, Google ADK — each gives the agent **a shell + file reader + grep** and lets Circle's own skills (fetched from `https://agents.circle.com/skills/setup.md`) drive the `circle` CLI. This file is the natural place to plug a **Ledger tap** instead of `y/N` (see idea I).

**Paymaster.** Permissionless ERC-4337 v0.7/v0.8 paymasters that let users pay gas in USDC: Arbitrum, Base (v0.7) and Arb/Avax/Base/Eth/Op/Polygon/Unichain (v0.8); 10% surcharge on Arb/Base. **Not deployed on Arc** — and on Arc gas *is* USDC, so it's moot there. ### 1.3 Privy

**Products relevant here (all via `@privy-io/node`, REST, or Dashboard):**

- **Wallets** with an *owner* (user, P-256 authorization key, or **key quorum**) and *additional signers* each with `override_policy_ids`. Owners can update policies/signers/export; signers can only sign/transact within their policy. Wallets are Shamir-split, reconstituted in TEEs.
- **Key quorums** — `privy.keyQuorums().create({ public_keys, user_ids, key_quorum_ids, authorization_threshold, display_name })`; m-of-n; can mix users and server keys; **nested one level** ("Security Team" inside "Org Admins"). Sign requests by passing multiple signatures in `privy-authorization-signature` or via `authorization_context: { authorization_private_keys: [...], user_jwts: [...] }`. Docs label them "an advanced feature — reach out on Slack", but the API and Dashboard flows are public.
- **Organizations** — `privy.organizations().create({ display_name, default_key_quorum_id })`; wallets created with `entity: { id: orgId, type: "organization" }` get the org's default quorum as owner (≤150 wallets/org; entity is immutable). Pattern: default quorum = locked-down admins; extra lower-privilege quorums attached as `additional_signers` with scoped policies ("can send < 1000 USDC on Tempo").
- **Intents** — asynchronous authorization: `POST /v1/intents/wallets/{id}/transfer` (or `/rpc`, `update-wallet`, `update-policy`, `update-key-quorum`) creates a pending intent with just the app secret; signers append signatures over time (client SDK with the user's JWT, or server keys); auto-executes at threshold. Statuses: pending → granted/processing → executed | failed | rejected | expired (**72 h default**) | dismissed (resource changed). Webhooks: `intent.created`, `intent.authorized`, `intent.executed`, `intent.failed`, `intent.rejected`. Dashboard **Approvals** page = out-of-the-box review UI with MFA, diff previews, deeplinks.
- **Policies** — `policy → rules → conditions`; each rule has `method` (`eth_sendTransaction`, `eth_signTypedData_v4`, `personal_sign`, `exportPrivateKey`, `transfer`, `earn`, `*`…), conditions with `field_source` ∈ `ethereum_transaction | ethereum_calldata (+abi) | ethereum_typed_data_domain | ethereum_typed_data_message (+typed_data) | ethereum_7702_authorization | action_request_body | message | system (current_unix_timestamp) | reference (aggregations) | solana_* | tron_* | sui_* | xrpl_* | tempo_*`, operators `eq neq lt lte gt gte in in_condition_set contains starts_with ends_with`, action ALLOW/DENY. **Condition sets** = reusable allow/deny lists (`in_condition_set`). **Stateful policies (aggregations)** = rolling-window sums (e.g., daily USDC out) referenced as `aggregation.<id>` — max 10 per app, `sum` only, only `eth_signTransaction`/`eth_signUserOperation`, updated *after* signing → "disaster prevention, not strict enforcement". Transfer-size limits require simulation and run at the API layer, not in the enclave. **x402 payments are EIP-712, so `eth_sendTransaction` rules don't cover them** — write `eth_signTypedData_v4` rules on `ethereum_typed_data_domain.verifyingContract` / `ethereum_typed_data_message.to`.
- **Wallet actions**: `/transfer` (human-readable asset/amount/chain/destination; **native bridging + same-peg stablecoin conversion**; chains: Ethereum, Base, Arbitrum, Polygon, Tempo, Robinhood, Solana, Tron + their testnets — **no Arc**), `/swap` (EVM mainnets incl. Base/Arb/Op/Polygon/Unichain/Tempo + Sepolia/Base Sepolia/Unichain Sepolia/Monad testnets — **no Arc**; requires gas sponsorship), **Earn** (`/earn/ethereum/vaults/{vault_id}/deposit|withdraw|position`; **self-serve vaults in Dashboard = Morpho: Gauntlet USDC Prime and Steakhouse Prime Instant (USDC on Base mainnet), Sentora PathUSD (Tempo)**; Aave/Veda/TMMF vaults need sales), fiat payouts (Bridge KYB), fiat/crypto deposit accounts, onramp modal (Stripe/MoonPay self-serve for USD/EUR/AUD/BRL; Meld needs KYB), Cards (guided onboarding — mock allowed but not the qualifying flow), monetization fees (swap/transfer fee = early access).
- **Chain support tiers**: Tier 3 (sign+broadcast) = "Ethereum incl. EVM-compatible networks", Solana, Tempo → **Arc works via raw RPC `eth_sendTransaction`/`eth_signTypedData_v4` with `caip2: "eip155:5042002"`** (needs USDC in the wallet for gas). Policies need Tier 2+ (EVM ok). Managed actions need Tier 3 *and* provider coverage (Arc: no).
- **Agent tooling**: Agent CLI `@privy-io/agent-wallet-cli` + sandbox `agents.privy.io` (OAuth device-code login, ephemeral signing keys, OS credential manager or encrypted `~/.privy/session.json`); `createX402Client(privy, { walletId, address })` in `@privy-io/node/x402` + `@x402/fetch` `wrapFetchWithPayment` (Base, Base Sepolia, Solana per docs; `maxValue` cap; `signatureOptions: {type:'erc1271'}` for smart wallets); MPP support; execution wallets (EIP-7702 fleets); webhooks for balances/transactions; gas sponsorship via Kernel/Pimlico smart wallets or app-pays.

**Maturity / gating summary.** GA and self-serve: server wallets, policies, condition sets, aggregations, authorization keys, key quorums (API+Dashboard, "reach out" language but no hard gate found — verify in the dashboard on day 1), organizations, intents, Dashboard approvals, `/transfer` incl. bridging/conversion, swaps (mainnet + a few testnets), Earn on the three listed vaults (mainnet, real money), Agent CLI, x402 client, webhooks. Gated/commercial: Cards, fiat deposits/payouts (Bridge KYB), TMMF/Aave/Veda vaults, custom transfer/swap fees, Meld onramp.
**Time to first tx:** dashboard app + server wallet + policy + Sepolia tx **~1 h**; org + 2-of-3 quorum + intent approved in Dashboard **2–4 h**; Earn deposit into a Base Morpho vault **1–2 h + a few real USDC + gas sponsorship enabled**.

### 1.4 Ledger Agent Stack (Wallet CLI, Key Ring, DMK, skills)

**Three pillars.** (1) **Wallet CLI** `@ledgerhq/wallet-cli` v2.1.0 (2026-07-30; native Bun binaries for darwin-arm64, linux-x64/arm64, windows-x64; source `LedgerHQ/ledger-live/apps/wallet-cli`) — commands `account discover`, `session view|reset`, `balances`, `operations`, `receive`, `send`, `swap quote|execute|status`, `assets token|token-by-id`, `earn yields|positions|deposit|withdraw` (ERC-4626 vaults, Solana staking), `genuine-check`, **`ring init|encrypt|decrypt|keys|destroy`**, `skill list|retrieve|install|doctor`. Networks: bitcoin, ethereum, solana (+ `ethereum:sepolia`, `bitcoin:testnet`, `solana:devnet` for discover). The agent skill explicitly declares **send/receive/swap on testnets and L2s "out of scope"** and the CLI cannot target Arc. Every fund-touching command needs a device tap; read-only ones don't. (2) **DMK skills** (`npx skills add ledgerhq/agent-skills -s ledger-dmk-implementation dmk-intent-vocabulary dmk-business-logic`) — markdown that teaches a coding agent to wire the **Device Management Kit** into an app with a 5-step process (Init → Session → Device State → App Management → Operation) and HITL gates. (3) **Hardware security**: OpenPGP app (tap-per-decrypt mode) and FIDO2 Security Key app.

**Key Ring (`wallet-cli ring`) — what it actually does (read from source).**
- `ring init [--name <member name, default hostname>] [--unsecure-no-password]`: generates an LKRP **member keypair** (`sdk.initMemberCredentials()`), then with the device + **Ledger Sync app** open runs `sdk.getOrCreateTrustchain(deviceId, creds)` (creates the trustchain root on the seed or joins the existing one, opening the wallet-cli branch at **`m/0'/17'/0'`**, `applicationId 17`; Ledger Sync uses 16 on the same root). Stores the member private key (AES-256-GCM-wrapped with PBKDF2 of your password, `ENC:` prefix) in the **OS keychain** via `@napi-rs/keyring` (service `ledger-wallet-cli`, account `member-private-key-<hash of state dir>`), and `{rootId, applicationPath}` + `passwordSalt` in `~/.local/state/ledger-wallet-cli/session.yaml`.
- `ring encrypt|decrypt --key <name> [-i in] [-o out]` (or stdin/stdout): loads creds from keychain (password from TTY or **`WALLET_PASS`** env in non-TTY), calls **`sdk.restoreTrustchain()`** (network: challenge → member-key auth → JWT → fetch tree → derive `walletSyncEncryptionKey`), then `HKDF-SHA256(info=<key name>)` → AES-256-GCM. **No device**, network required, key never persisted. Wire format `[12-byte IV][ciphertext]`.
- `ring keys` lists key names used; `ring destroy` closes the application stream / tears down (typed "destroy" confirmation; `echo destroy | wallet-cli ring destroy`).
- Removing a member **rotates** the key (new path `m/0'/17'/1'`) → old ciphertexts undecryptable → re-encrypt.
- `WALLET_CLI_MOCK=1` switches to an in-memory mock LKRP SDK (good for tests, not demos).
- **There are no `ring members list|add|remove|enroll` commands** — but the public, STABLE npm packages `@ledgerhq/ledger-key-ring-protocol` (0.15.2) and `@ledgerhq/hw-ledger-key-ring-protocol` (0.10.7) expose the full **TrustchainSDK**: `initMemberCredentials()`, `getOrCreateTrustchain()` (device), `restoreTrustchain()`, `getMembers()`, **`addMember()` — "no hardware, uses a SoftwareDevice"**, `removeMember()` (device → rotation), `destroyApplication()`, plus the **QR-code pairing protocol** (WebSocket relay `GET /v1/qr`, ECDH session key, digit code) that Ledger Sync uses to add a second device *without a hardware wallet on the second device*. `LkrpIdentityProvider` takes a credentials callback "allowing headless consumers to load secrets from external storage". Trustchain API: `GET /v1/challenge`, `POST /v1/authenticate`, `GET /v1/trustchain/{id}`, `PUT /v1/trustchain/{id}/commands`, …
- **Implication (the whole Ledger "no USB port" prompt):** on a headless Linux VPS/CI runner, wallet-cli's ring is blocked twice — no USB for `ring init`, and **no Secret Service/D-Bus keychain** for `@napi-rs/keyring`. The protocol, however, already supports enrolling a new member from an existing member (software-signed `AddMember` + `PublishKey`), and revoking it with a device tap (rotation). Nobody has shipped that as a CLI surface yet.

**DMK for headless/Node** (`@ledgerhq/device-management-kit` 1.9.0, `@ledgerhq/device-transport-kit-node-hid` 1.0.1 ("under development"), `@ledgerhq/device-signer-kit-ethereum` 1.18.0, `device-transport-kit-speculos` 1.2.1 for the emulator). Eth signer: `getAddress(path, {checkOnDevice, chainId})`, `signTransaction` (clear signing with the context module; `originToken` from Ledger only needed for Transaction Check), `signMessage`, **`signTypedData(path, typedData)` (EIP-712)**, `signDelegationAuthorization` (7702), Safe display. Observable-based API; user-interaction steps surfaced (`UserInteractionRequired.SignTypedData` etc.). Clear-signing metadata for **Arc (chain 5042002) will be missing** → device shows raw fields / "unknown network"; a native USDC transfer on Arc is a plain value transfer that the Eth app will render as an 18-decimal native amount (confusing on screen) — EIP-712 messages render field by field and are the cleaner HITL surface **(inferred from app behavior; verify on device day 1)**.

**Ledger Wallet Provider** (web, first-party pairing UI, Clear Signing, Transaction Check) is for browser dapps — useful if you want a Ledger-connected web frontend.

**Maturity.** wallet-cli 2.x is "stable" for its scope; ring shipped in 2.0 (July 2026) and the docs still say "early development, breaking changes possible". DMK is production (Ledger Live uses it) but node-hid transport is labelled under development. Time to first: `ring init` + encrypt/decrypt **~30 min** with a device that has the Ledger Sync app installed (via Ledger Live "My Ledger"); DMK node-hid + Eth `signTypedData` from a Node script **2–4 h**; a Ledger-signed x402 nanopayment on Arc testnet **~1 day**.

**What the Ledger judges want (decoded).** Their bullets are unusually specific: (1) "**a broker hands out scoped capabilities, never the API key**" (2) "**enroll a VPS, a CI runner, or a hosted agent**" into the Key Ring — both "must be built on … the Ledger Key Ring CLI (`wallet-cli ring`)"; (3) x402-style Ledger-secured payments; (4) device approval before funds move or permissions escalate. Plus: "clear boundaries between autonomous behavior and explicit approval", "concrete use of Ledger primitives, not just wallet branding", "something we can run without you in the room", and **DX feedback is judged as much as code**. The Continuity bullet "make `wallet-cli ring` the key backend for the `.env`, `sops`, or `age` files your repo already has" tells you they'd love a sops/age-style integration.

### A. 🔴 **Ringmaster** — headless Key Ring enrollment + a capability broker for agents
**Pitch.** Make `wallet-cli ring` usable where the Ledger track says it isn't: on a VPS, CI runner, or hosted agent with no USB port and no OS keychain. On the host, a small **broker daemon** loads the member key from a headless keystore (file/TPM/KMS), `restoreTrustchain`s, decrypts `.env.enc`/`secrets.enc` **into memory only**, and hands agents **scoped capabilities instead of secrets**: a local HTTP proxy that injects the real API key for allowed host/path/method, with per-capability rate and spend caps and TTLs; the agent only ever sees `cap_…` tokens. **Escalation** (new host, higher cap, decrypt a new key name) produces an EIP-712 `CapabilityGrant` the human **clear-signs on the Ledger** (DMK `signTypedData`), which the broker verifies against the enrolled Ledger address. **Revocation** = `ring members remove vps-1` on the laptop (device tap → key rotation) → the host's next `restoreTrustchain` fails with "Key Ring rotated"; re-encrypt with one command. Ship as (1) a PR-shaped extension to wallet-cli (`ring members list|add|remove`, `ring enroll --from <laptop>`, `--keystore file|tpm|kms`) and (2) a standalone `ringmaster` broker using the SDK directly, plus a sops/age-style `ring exec -- <cmd>` that injects decrypted vars into a child process.
